# 文章模板与写作约定

这份文档有两个用途：给你一个可以直接复制的空模板；以及约定「把草稿交给 AI 整理」时，最终会输出成什么样。

## 空模板

复制到 `src/content/posts/<slug>.md`（slug 用小写英文和连字符）：

````markdown
---
title: '文章标题'
description: '一两句话摘要，会出现在卡片和搜索引擎里'
published: 2026-11-24
category: 技术
tags: ['Astro', '前端']
cover: /covers/aurora.jpg
coverAlt: '封面图的描述'
---

开头先给结论或场景，别急着铺垫。

## 一级小标题

正文一段一个意思，段落之间空一行。

### 更细的分支

- 列表只用来列并列项
- 需要解释的用段落，不要硬塞进列表

## 代码

```ts
const answer = 42;
```

## 收尾

一句话总结，或指向下一篇。
````

## frontmatter 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `title` | 是 | 标题，尽量具体，不用「浅谈」「漫谈」 |
| `description` | 否 | 60–90 字，决定卡片摘要与 SEO 描述 |
| `published` | 是 | `YYYY-MM-DD`，决定排序 |
| `updated` | 否 | 有实质修改时再加 |
| `category` | 否 | 单选：技术 / 随笔 / 生活 / 阅读 … |
| `tags` | 否 | 复用已有标签，别为每篇造新词 |
| `cover` | 否 | 不填用 `/covers/aurora.jpg` |
| `coverAlt` | 否 | 封面的替代文本 |
| `draft` | 否 | 草稿，生产构建不输出 |
| `pinned` | 否 | 首页置顶 |

## 格式约定

整理草稿时默认遵循下面这些规则，有冲突以你的要求为准。

1. **标题层级**：文章标题放 frontmatter，正文从 `##` 开始，最多到 `####`，不跳级。
2. **段落**：一段一行，不在句中断行；段间空一行。
3. **代码**：必须标注语言（`ts` / `bash` / `css` / `json` …）；省略内容用 `...`，不用「此处省略」。
4. **中英混排**：中英文之间留一个空格；中文使用全角标点；数字与单位之间不加空格。
5. **链接**：链接文字要有意义，不写「点这里」；外部链接会自动新窗口打开。
6. **图片**：`alt` 写清楚内容；需要图注时用 `<figure><img …><figcaption>…</figcaption></figure>`。
7. **列表**：嵌套不超过两层；步骤类内容用有序列表。
8. **术语**：首次出现给英文原文，之后统一用中文或缩写。
9. **不确定的内容**：用 `<!-- TODO: 待确认 -->` 标出来，不凭空补事实。

## 把草稿交给我

直接把原始内容发过来即可（手写笔记、语音转文字、几段链接、零散想法都可以），最好附上：

- 想放哪个 **分类**、打哪些 **标签**
- 要不要 **置顶** / 指定 **封面**
- 偏好的语气（技术笔记 / 随笔 / 教程），默认沿用你已有文章的风格

我会返回：

- 一份完整的 Markdown，字段齐全、层级正确
- 标题与 `description` 的建议
- 需要你确认的地方（用 TODO 标出，不擅自编造）

整理完成后，把文件放进 `src/content/posts/`，运行 `npm run dev` 看效果；发布前跑一次 `npm run build`，确认搜索索引也能正常生成。

## 发布前检查

- [ ] 文件名是英文 slug，且没有和旧文章重名
- [ ] `description` 能独立说清这篇讲什么
- [ ] 代码块语言标注正确，长行没有超出容器
- [ ] 标签复用了已有标签，没有制造同义词
- [ ] 移动端看过一遍（窄屏下图、表格、代码块是否可读）
- [ ] `npm run build` 通过
